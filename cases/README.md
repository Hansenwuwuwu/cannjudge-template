# case 优化记录

一个 case 一个 md，记录这个 case 试过的所有优化思路和结果。

## 什么时候建

第一次对这个 case 做优化时，复制 `_template.md` 改名：

```
cases/
├── README.md        本文件
├── _template.md     空模板
├── case3.md
└── case8.md
```

命名就是 Judge 里的 case 序号：case1、case2……数量按当前题目，不预设。

## 内部怎么组织

**按优化思路分类，不按时间流水账。** 二级标题是方向，三级标题是某次尝试：

```markdown
# case8

## 概况

| 项 | 值 |
| --- | --- |
| shape | (5, 17, 33) |
| 基线用时 | 9.00 µs |
| 当前最好 | 6.00 µs |
| 已试方向 | 访存、归约 |

## 访存：Gather 索引

### 2026-11-12 003_c8_split32 —— 常量位模式替掉运行时索引

- 假设：每行固定开销来自 SetValue 构造索引
- 改动：GatherMask 常量位模式 + count 模式
- 结果：9.00 → 6.00 µs，9/9 通过
- 结论：保留

## 归约

### 2026-11-13 005_c8_pair_reduce —— 两两归约省掉尾 lane

- 假设：尾 lane 参与归约多做了一次全宽
- 改动：MulAddDst 折尾
- 结果：6.00 → 5.70 µs
- 结论：保留
```

同一个方向试了多次就往下排，失败了也留着，标「回退」。

## 一条记录写什么

| 字段 | 内容 |
| --- | --- |
| 日期 + 版本 | 对应 `optimize/versions/<版本>` 和 `PROGRESS.md` 里那一段 |
| 假设 | 为什么觉得这里慢，期望降多少 |
| 改动 | 具体到函数、指令、参数 |
| 结果 | 九点里这个 case 的前后用时；失败就写错误现象 |
| 结论 | 保留 / 回退 / 待验证 |

「结果」写实际读数，不要写「变快了」。判不出效果就写「9.00 → 8.90，在噪声内」。

## 和 PROGRESS.md 的分工

- `optimize/PROGRESS.md`：这次提交整体怎么样，两三行，带一个指向本目录的链接
- `cases/caseN.md`：这个 case 具体改了什么、为什么、读数多少

同一次提交，两处都要写。PROGRESS 里写不下时才展开到这里；这里的每条都要能对应到 PROGRESS 里的一个版本。

## 注意

- 不要只记录成功的尝试。失败的假设同样值钱，能防止下一个人重试。
- 结论是「回退」的条目，代码可以删，记录必须留。
- 一个 case 的记录超过一屏时，先看「概况」表能不能回答「当前最好多少、试过哪些方向」。
